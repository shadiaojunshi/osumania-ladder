## A. 难度色板调整

**问题:** 当前 [data/scales/reform-dan.json](../../data/scales/reform-dan.json)
在 7~10 区间(rf7..rf10+)黄色区段太薄,从绿到橙过渡里"黄"被一带而过,
辨识度低。

**目标色谱(用户口述 + 第二轮微调,扩宽红段):**

口述基线是"η~ε 黑 / δ~γ 紫 / β 红 / α 橙 / 10~9 黄 / 8 黄绿 / 7 绿 /
6~5 蓝绿过渡 / 4~1 蓝至淡蓝"。第二轮反馈"红的区域又太少了",
所以把红的家族从 β 单段扩到 γ- ~ α+ 五级。

| 段 | 色调 |
|---|---|
| η+/η/η- | 黑 |
| ζ+/ζ/ζ- | 黑(向深黑紫过渡) |
| ε+/ε/ε- | 深黑紫 |
| δ+/δ/δ- | 深紫 |
| γ+ | 紫 |
| γ | 紫偏红 |
| γ- | **紫红 / 红紫**(进入红家族) |
| β+ | **红** |
| β | **红(最红的核心)** |
| β- | **红橙** |
| α+ | **橙红**(还在红家族) |
| α | 橙 |
| α- | 橙偏黄 |
| 10+/10/10- | 黄橙 → 黄 |
| 9+/9/9- | **黄(核心黄段,加宽)** |
| 8+/8/8- | 黄绿 |
| 7+/7/7- | 绿 |
| 6+/6/6- | 偏蓝一点的绿(蓝绿) |
| 5+/5/5- | 偏绿一点的蓝(绿蓝) |
| 4+/4/4- | 蓝(**注意:全程不出现深蓝**,4 是亮度较高的蓝) |
| 3+/3/3- | 开始向淡蓝过渡 |
| 2/1/intro | 淡蓝至接近白 |

**实施:**
- 改 [data/scales/reform-dan.json](../../data/scales/reform-dan.json) 每个 level 的
  `color` 字段。numericValue 不动,只动 hex。
- 改完跑 `npm run build` 验证渲染管线无 regression([src/lib/difficulty.ts:16-27](../../src/lib/difficulty.ts#L16-L27)
  会按相邻两段 hex 做线性插值,所以新色板要相邻 hex 在 RGB 空间过渡平滑,
  不要出现"黄绿 → 红"这种跳变)。
- 验证方式:本地 `npm run dev`,主页随便切几个比赛,对照"色块整体观感是不是符合
  上面的口述"。

**关联:** 夜间模式选了"统一 CSS filter 降亮",但用户先要重调 light mode
原色,再叠 filter。所以 A 要先于 B。

要点:

## D. "每轮键型" 重叠总宽不变

**问题:** 上次反馈批 #2 里把同行重叠从 2-way 扩到 N-way 后([src/components/ladder/LadderView.tsx](../../src/components/ladder/LadderView.tsx))
重叠时格子总宽会比不重叠的格子大一些 — 不美观。

**方案:** **等分单元格宽,变窄。** N-way 重叠时,每个 box 宽 = `cellWidth / N`,
总宽与不重叠时相同。

**实施:** 看 LadderView 里"每轮键型"模式的布局段(用 `overlapInfo` 的部分),
找到 N-way 时 box 当前宽度计算,改为基础 cellWidth 除以重叠数。

### 实施记录 (2026-06-10)

改动点:[src/components/ladder/LadderView.tsx:553-559](../../src/components/ladder/LadderView.tsx#L553-L559)。

原本:
```tsx
const left = info ? `${(info.idx / info.size) * 100}%` : '4px'
const right = info ? `${((info.size - info.idx - 1) / info.size) * 100}%` : '4px'
```
重叠时左右用纯百分比,N 个 box 拼起来正好填满 100%(整个 cellWidth);
不重叠时则两侧各留 4px。所以重叠总宽 = cellWidth,不重叠总宽 =
cellWidth - 8px,**重叠反而比不重叠更宽**。

改后:
```tsx
const left = info
  ? `calc(4px + (100% - 8px) * ${info.idx / info.size})`
  : '4px'
const right = info
  ? `calc(4px + (100% - 8px) * ${(info.size - info.idx - 1) / info.size})`
  : '4px'
```
不论重叠与否,可用区间都是 `cellWidth - 8px`(两侧各 4px 内边距);
重叠时把这条区间等分给 N 个 box,每个宽 `(cellWidth - 8) / N`。

`npm run build` 通过。

未跟进:**N 太大、cellWidth 太窄时 box 内文字会溢出**。设计文档原本预留
"低于 18px 走 hover 展开"的降级阈值,本次未做。等遇到实际反馈再加。

**未定:** 当 cellWidth/N 太窄(比如 N=4 在 480px 屏),box 内文字可能溢出。
留意,先实现等分,真出问题再加阈值降级(比如低于 18px 就走 hover 展开)。

## E. 参考点公式难度输入

**动机:** SV 段没有标准 dan/rf scale 可对应,用户当前要硬填一个数字其实是
凭感觉。新机制把"参考某场权威赛事的某轮"作为锡点,在两轮之间三等分,
得到 +1/3 或 +2/3 这种"中间档位"。同样的机制对 RC/LN/HB 也开放,作为
非主要的辅助输入方式。

**用户给的例子:**
> 选择"MWC Ro32+",自动算 = `MWC Ro32 难度 + (Ro16 难度 - Ro32 难度) / 3`
> 选择"Ro16-",自动算 = `MWC Ro32 难度 + (Ro16 难度 - Ro32 难度) * 2 / 3`

简言之:把同一赛事相邻两轮(Ro32 ↔ Ro16)之间的难度差三等分,落在中间的
两个分位用"+ / -"表达。

### 数据模型

slot 的 `difficulty` 字段从单一 number 改为 union:

```ts
type SlotDifficulty =
  | number  // 原始手填
  | {
      kind: 'reference'
      leftRefId: string   // 例如 'mwc-2024:ro32:RC'(轮次 + 键型 复合)
      rightRefId: string  // 'mwc-2024:ro16:RC'
      position: 0 | 1 | 2 | 3  // 0=左锡点 1=+1/3 2=+2/3 3=右锡点
      // 实际渲染时:left + (right - left) * position / 3
    }
```

`difficultyLn`(LN 双值的 LN 段)同结构,独立字段。

### 参考赛事 manifest

**营运方式:** Admin RoundEditor 里加勾选字段 "作为参考锡点"。
被勾的轮次在所有键型对应的"轮次平均难度"上自动注册为可被引用的锡点。
在 `data/reference-tournaments.json`(或直接生成进 tournaments-data.json
的额外字段)里登记 `(tournamentId, roundId, type)` → 计算出的难度数。

锡点 ID 格式建议:`<tournamentId>:<roundId>:<type>` 例如 `mwc-2024-4k:ro32:RC`。

可选锡点列表 = "勾选过 isReferenceRound = true 的轮次" × "该轮包含的所有键型"。
列表按比赛年份倒序、轮次顺序(Qual → GF)排列。

### Admin UI

slot 内 difficulty input 加一个**模式切换** radio:
- "数字" — 当前的手填数字
- "参考锡点" — 反转出来下面三层:
  - left ref dropdown(从可选锡点列表选)
  - right ref dropdown(同上,默认填 left ref 同比赛同键型的下一轮)
  - position radio: `0 | +1/3 | +2/3 | 1`(展示为左锡点本身 / 1/3 / 2/3 / 右锡点本身)

切换"数字"→"参考锡点"时清空数字,反之亦然。两种模式不并存。

### 实时重算

锡点难度变了(例如 admin 改了 MWC Ro32 RC 的某张谱面),所有引用它的
slot 在下一次主页加载时自动取到新值,**不需要手动同步**。
实现:`getSlotDifficulty(slot)` 函数集中处理 union,在每次渲染时按公式 + 当前
锡点 manifest 取值。锡点 manifest 在 build 时(`scripts/generate-tournaments.js`)
预计算并嵌入 generated tournaments,运行时无需查 JSON。

### 显示

"每轮键型"模式下色块的 hover tooltip / HoverCard 显示
`参考: MWC 2024 Ro32+ (≈ 7.33)` 而不是裸数字,让人能追溯。
"每场比赛" / "每轮图池" 模式下不变,看到的就是数值。

### 未定 / 后续

- 参考锡点列表过长怎么办 — MVP 先全列出,以后做分组(按比赛分类、搜索过滤)。
- 跨键型引用是否合理(用 RC 锡点推 SV slot 难度?)— 不限制,但 UI 上 left+right 必须
  同键型,跨键型用户自负。
- 参考锡点形成环或自引用 — 防御:`leftRefId` / `rightRefId` 都不能指向当前 slot 自己
  所在的 round + type,build 时校验。

### Tailwind v4 dark 模式

v4 不用 `tailwind.config.ts` 的 `darkMode: 'class'`(项目里也确实没有这个文件),
而是在 [globals.css](../../src/app/globals.css) 里加:

```css
@import "tailwindcss";
@custom-variant dark (&:where(.dark, .dark *));
```

之后 `dark:bg-neutral-900` 这类 utility 才会响应 `<html class="dark">`。

### 首屏零闪烁 inline script

主题 + 语言两个偏好 都从 localStorage 读,**合并到一段同步 script**
(避免两段 script 重复读 localStorage),放在 layout.tsx `<head>` 里:

```html
<script dangerouslySetInnerHTML={{ __html: `
  (function(){
    try {
      var t = localStorage.getItem('theme');
      if (!t) t = matchMedia('(prefers-color-scheme: dark)').matches ? 'dark' : 'light';
      if (t === 'dark') document.documentElement.classList.add('dark');
      var l = localStorage.getItem('lang');
      if (!l) l = (navigator.language || '').toLowerCase().startsWith('zh') ? 'zh' : 'en';
      document.documentElement.lang = l === 'zh' ? 'zh-CN' : 'en';
    } catch(e){}
  })();
`}} />
```

这样 SSR 出来的 html 主体仍是默认的(便于缓存),客户端在 hydration 之前
class 和 lang 已被脚本同步注入,不会先看到浅色 / 中文再切回去。

### 偏好 store

主题 + 语言可以共用一个 zustand store(`src/stores/prefsStore.ts`),
两个字段都 `persist` 到 localStorage,中间件用 `zustand/middleware`。
首次 hydrate 时和 inline script 已经写入的 `<html>` 状态保持一致。
